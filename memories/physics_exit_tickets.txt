PHYSICS EXIT TICKETS BUILD — PORTABLE MEMORY / GOLD STANDARD
================================================================

PURPOSE
-------
THIS FILE IS THE CURRENT SINGLE SOURCE OF TRUTH FOR PHYSICS EXIT-TICKET BUILDS.

The finalized Unit 1 exit-ticket package is the gold-standard interpretation for:
  • source grounding
  • three exit tickets per section
  • four questions per ticket
  • coverage of the section I-can statements
  • DOK balance
  • projector-first layout
  • 2x2 question-table architecture
  • first-screen navigation menu
  • anchor/link naming
  • Physics diagrams
  • CSS usage
  • print behavior
  • ZIP/deployment structure
  • QA

The approved Unit 1 build established this core model:
  • Unit 1 has 5 sections.
  • Each section has Ticket A, Ticket B, and Ticket C.
  • Therefore Unit 1 contains 15 exit tickets total.
  • Each ticket has exactly 4 questions.
  • The four questions collectively cover the section's I-can statements.
  • Questions are primarily DOK 1 and DOK 2.
  • A ticket MAY include one DOK 3 question when the section target naturally supports strategic reasoning.
  • No ticket may contain more than one DOK 3 question, and DOK 3 should NOT appear on every ticket.
  • There is NO student workspace because students answer on a separate generic form.
  • Questions are displayed in a literal 2x2 table to minimize space.
  • Every ticket is designed to fit inside one projector viewport without scrolling.
  • A full-screen landing/menu page appears first and links to every ticket.
  • Physics diagrams may be embedded directly as inline SVG.
  • The approved Unit 1 package uses 13 embedded force diagrams; this is NOT a quota.
  • The current shared external exit.css is the layout authority and is not bundled in unit ZIPs.

"BUILD," "CREATE," "MAKE," "GENERATE," OR "REBUILD" MEANS COMPLETE THE FULL PACKAGE.
A plan, outline, question list, partial HTML, or preview is not a completed build.

================================================================
ASSESSMENT PLAN = CONTENT / TIMING CONTRACT
================================================================

The assessment plan controls what students should know by each section and what each
I-can statement actually means.

Before planning the three tickets for one section:

1. List ALL I-can statements for the section.
2. Identify the exact concepts, vocabulary, formulas, and representations that support
   each I-can statement.
3. Identify which formative/summative question families are already eligible by this
   point in the unit.
4. Use notes to verify that a proposed question does not require later-section content.
5. Build three genuinely parallel ticket forms that sample the section's full target set.

HARD RULE:
Never pull later-section Physics content into an earlier section just to make a question
more interesting or to satisfy a DOK target.

If the existing assessment bank does not provide enough suitable exit-ticket prompts,
create original questions grounded in the CURRENT section's I-can statements and notes.
That is the correct response; do not reach ahead.

================================================================
CORE EXIT-TICKET ARCHITECTURE — LOCKED DEFAULT
================================================================

PER SECTION:
  Ticket A
  Ticket B
  Ticket C

PER TICKET:
  exactly 4 questions
  arranged as a literal 2x2 table
  no workspace
  no answer lines
  no name/date fields
  no student response boxes

PER UNIT:
  total ticket count = 3 x number of sections in the current assessment plan.

For a five-section unit:
  15 tickets total.

Do not silently invent or delete sections to force 15 if a future assessment plan uses a
different section count.

================================================================
I-CAN COVERAGE
================================================================

The PURPOSE of each four-question ticket is to give a compact read on the section's
learning targets.

APPROVED UNIT 1 INTERPRETATION:
Unit 1 sections have four I-can statements, so Questions 1–4 map in order to I-can 1–4.

For a future section with exactly four I-can statements:
  Q1 -> I-can 1
  Q2 -> I-can 2
  Q3 -> I-can 3
  Q4 -> I-can 4

Across Ticket A/B/C, preserve that broad four-target coverage while changing the actual
student-facing task.

If a future section has a different number of I-can statements:
  • keep exactly 4 questions unless the user explicitly changes the standard
  • distribute the four questions as evenly and instructionally as possible
  • make sure every I-can appears somewhere across the three forms
  • do not invent a learning target merely to create a 1:1 mapping

A ticket should not accidentally become four versions of one narrow skill.

================================================================
DOK STANDARD — HARD RULE
================================================================

Default exit-ticket cognitive demand:
  • Most questions should be DOK 1 and DOK 2.
  • A four-question ticket MAY contain one DOK 3 question.
  • A four-question ticket may NOT contain more than one DOK 3 question.
  • DOK 3 should be used selectively; do NOT include a DOK 3 question on every ticket.
  • No DOK 4 unless the user explicitly changes the standard.

APPROVED UNIT 1 COUNTS:
  60 total questions
  12 DOK 1
  47 DOK 2
   1 DOK 3

Those exact 12/47/1 counts are a Unit 1 RESULT, not a required quota for future units.
Unit 1 happened to use only one DOK 3 question. Future units may use more than one DOK 3
question across the unit, provided each individual four-question ticket contains at most one
DOK 3 item and DOK 3 is not forced into every ticket.

DOK 1:
  • recall
  • identify
  • recognize
  • classify
  • name a force/term
  • simple one-step interpretation

DOK 2:
  • apply a familiar concept
  • compare evidence
  • interpret a familiar diagram/model
  • calculate/interpret net force in a routine situation
  • explain a familiar relationship briefly
  • connect motion language to a familiar force condition

DOK 3 — SELECTIVE, MAXIMUM ONE PER TICKET:
  • strategic reasoning
  • diagnose a conflict or misconception
  • revise a model using evidence
  • compare/critique competing representations

Use DOK 3 only when it genuinely fits the I-can statement and available instruction.
Do not add complexity merely to satisfy a quota. Some sections or forms may have no DOK 3
question at all.

Do not inflate a question to DOK 3 merely by adding "explain."
Do not hide a DOK 3 question in multiple choice and then tag it as DOK 2 merely because it
has answer choices.

In the approved Unit 1 package, the only DOK 3 item happened to be the final question of
Ticket C in Section 1.5. It asks students to identify a conflict between a constant-speed
description and an unbalanced force model and then revise the model. This is a historical
Unit 1 design choice, NOT a one-per-unit rule.

================================================================
PARALLEL-FORM STANDARD — TICKETS A/B/C
================================================================

Ticket A, Ticket B, and Ticket C for the same section are PARALLEL FORMS.
They should assess the same section targets at approximately the same overall difficulty,
but they must not be near-duplicates.

Across A/B/C, vary several of:
  • context
  • wording structure
  • prompt direction
  • representation
  • answer format
  • numerical values when meaningful
  • misconception targeted
  • diagram type or object
  • evidence presented

BAD PARALLELISM:
  "A 20 N force acts right..."
  "A 25 N force acts right..."
  "A 30 N force acts right..."

BETTER PARALLELISM:
  • one form uses a short scenario
  • one form uses a force diagram
  • one form uses a claim/error correction
while preserving the same I-can target and approximate DOK.

A student should not be able to use Ticket A as a near-identical answer key for Ticket B
or Ticket C.

================================================================
QUESTION-WRITING STANDARD
================================================================

EXIT TICKETS ARE PROJECTED, NOT PRINTED WORKSHEETS.
Questions must be concise enough to read from across the room.

Prefer:
  • one compact prompt
  • one clear task
  • short scenarios
  • familiar quantities
  • brief explanation demands
  • visually readable diagrams

Avoid:
  • paragraph-length setups
  • unnecessary data
  • giant answer-choice blocks
  • tiny text to rescue an overlong question
  • long multi-part calculations
  • wording that requires students to copy large amounts of information before solving

NATURAL WORDING
---------------
Avoid a Mad-Lib bank.
Rotate among:
  • direct / standard wording
  • action- or question-first wording
  • short real-world contexts
  • diagram/model interpretation
  • claim/evidence reasoning

VOCABULARY VARIETY
------------------
Rotate among:
  • term -> definition/concept
  • definition/concept -> term
  • example -> concept
  • concept -> example

Do not make every vocabulary item "Which term means...?"

MULTIPLE CHOICE
---------------
Multiple choice is allowed but not required.
If used:
  • use uppercase A, B, C, D labels
  • one clearly best answer
  • plausible distractors tied to misconceptions
  • avoid joke/absurd choices
  • keep the choice block compact enough for projection
  • use fewer than four choices only when a true binary decision is instructionally better
    and the approved source supports that structure

The approved Unit 1 exit tickets mix open response and selected response.

================================================================
NO WORKSPACE — HARD RULE
================================================================

Students answer on a separate generic response form.

Therefore the projected exit-ticket HTML contains:
  • NO .workspace divs
  • NO blank answer lines
  • NO textareas
  • NO response boxes
  • NO large empty regions reserved for writing

Screen space is for the four questions and any necessary representation.

================================================================
VISUALS / DIAGRAMS / GRAPHS
================================================================

VISUAL PHILOSOPHY
-----------------
Use a visual when it improves the question or assesses representation/modeling skill.
Do not add visuals as decoration and do not impose a fixed visual quota.

The approved Unit 1 package contains 13 embedded force diagrams because the force sections
benefit from them. The number 13 is NOT a future requirement.

Good exit-ticket visual uses:
  • unlabeled/neutral force diagrams
  • object + interaction arrows
  • motion arrow compared with force arrows
  • compact data table
  • short model comparison
  • true quantitative graph when the section actually teaches graph interpretation

VISUAL ANSWER-SAFETY — HARD RULE
--------------------------------
A figure may provide evidence but must never reveal the response students are supposed to
identify, label, classify, critique, or infer.

Before accepting a visual, ask:
  1. What is directly observable from the representation?
  2. What must the student calculate or infer?
  3. Does any label/title/caption/alt text give away the answer?
  4. Does the representation contain all information required by the prompt?
  5. Does the expected answer actually agree with the diagram?

Do not label a force "normal force" if the task is to identify the upward force.
Do not label a diagram "balanced forces" if the task is to decide whether forces balance.

PHYSICS DIAGRAMS
----------------
Force diagrams, motion arrows, generic object models, and other simple Physics schematics
are NOT coordinate graphs.

For these, use clean inline SVG when practical.
Advantages for this exit-ticket system:
  • self-contained HTML
  • no extra figure files
  • crisp at projector scale
  • easy to keep labels answer-neutral
  • exact sizing inside a 2x2 ticket cell

Approved Unit 1 force-SVG conventions:
  • viewBox approximately 720 x 230
  • class="force-svg"
  • object: rounded rectangle with class="obj"
  • support surface: class="surface"
  • force arrows: class="arr"
  • secondary/light arrows: class="arr-lite"
  • motion indicator: class="motion"
  • neutral unknown labels such as "?" are allowed
  • do not use arrow labels that reveal the target response

TRUE GRAPHS / graph_tool.py
---------------------------
Use the authoritative graph_tool.py only for genuine quantitative/data/axis graphs that
match one of its supported graph types.

If a true graph is required:
  1. Read graph_tool.py completely.
  2. Confirm an existing graph type fits the representation.
  3. Do NOT recreate a supported graph with ad-hoc matplotlib styling.
  4. Copy graph_tool.py byte-for-byte as generate_graphs.py if the current build workflow
     requires generation source.
  5. Append graph-generation blocks only below the final permitted append marker.
  6. Run it during QA.
  7. Inspect the actual output visually.
  8. Make sure the graph does not reveal the answer.
  9. Keep the projected ticket readable at full-screen scale.

Do NOT force a Physics diagram through graph_tool.py just because the tool is present.
If no true graph is instructionally needed, the exit-ticket package may contain no
figure PNGs and no generate_graphs.py. That is exactly what happened in the approved
Unit 1 build.

================================================================
FIRST PAGE / EXIT TICKET MENU — LOCKED
================================================================

The FIRST screen is a projector navigation menu.

It must:
  • fill one viewport
  • show every section
  • show Ticket A / Ticket B / Ticket C links for each section
  • fit without scrolling on the normal projector/desktop layout
  • use anchors that jump directly to each ticket

For a five-section unit, the menu shows five section rows and 15 ticket links.

Anchor naming standard:
  #exit-[unit]-[section]-a
  #exit-[unit]-[section]-b
  #exit-[unit]-[section]-c

Unit 1 examples:
  #exit-1-1-a
  #exit-1-1-b
  #exit-1-1-c
  ...
  #exit-1-5-c

Menu page id:
  id="exit-menu"

Menu link example:
  <a class="index-link" href="#exit-1-3-b">Ticket B</a>

The menu is for projection/navigation. In the approved CSS it is hidden when printing.

================================================================
PROJECTOR-FIRST SCREEN FIT — NOT ACCIDENTAL
================================================================

Every ticket is deliberately constrained to one projector viewport.
The gold-standard fit comes from ALL of these decisions working together:

  • .exit-ticket uses width: 100vw
  • .exit-ticket uses height: 100vh
  • overflow: hidden
  • flex column layout
  • compact fixed header
  • question table consumes the remaining height
  • exactly two rows x two columns
  • table-layout: fixed
  • each table row is 50% height
  • each table cell is 50% width
  • responsive clamp() font sizing
  • diagram max-height cap
  • compact choice layout
  • no workspace
  • question wording kept concise

HARD RULE:
Do not "solve" an overfull ticket by allowing scrolling on the normal projector layout.
Fix the question wording, choice length, figure size, or layout density instead.

The approved desktop/projector ticket uses:
  min-height: 620px

The approved narrow-screen fallback may become auto-height for usability, but the normal
classroom projector/desktop experience remains one screen per ticket.

================================================================
SCROLL / NAVIGATION BEHAVIOR
================================================================

The approved page uses vertical scroll snapping:

Do not remove scroll snapping unless the user explicitly changes the projection workflow.

     Ticket A: four targets

12. Link external ../../css/exit.css.
13. Open/render the HTML at a normal projector/desktop viewport.
