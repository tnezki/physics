Version: 1.0
Gold-standard prototype: Unit 1, approved August 16, 2026

PURPOSE
=======
This portable memory is the complete build contract for the Physics course Day 1 demos and Day 2 investigations.
It is intended to work in a brand-new chat with no prior conversation context.

Normal teacher workflow:

  "Read the PM, then build the demos and investigations (remember to output 2 separate zip files) for Unit 2"

The teacher will upload:
1. This portable memory text file.
2. The current authoritative graph_tool.py file.
3. The current unit notes ZIP.
4. The current unit assessment plan ZIP.

Those four uploads are sufficient.
Do NOT require the old physics archives, old textbook archive, Unit 1 prototype ZIPs, or CSS files to be uploaded again.
This PM carries forward the decisions and useful legacy catalog from the prototype process.

CORE COURSE WORKFLOW
====================
Each section follows this instructional rhythm:

Day 1:
- 5-8 minute demo / hook / discrepant event / quick phenomenon.
- Demo is used BEFORE the guided annotated notes.
- The class then completes the guided annotated notes together.

Day 2:
- 20-30 minute investigation in most sections.
- Investigation may be a hands-on lab, CER, Vernier Graphical Analysis activity, PhET / online simulation, modeling investigation, or another evidence-centered activity.
- A full 40-minute lab using the scientific method is appropriate when the content genuinely benefits from a full-period investigation.
- Students have already completed the section notes before the investigation.

The demo and investigation must serve different purposes.
Do not make Day 1 a miniature version of Day 2.

SOURCE PRIORITY / CONTENT AUTHORITY
===================================
For every unit build, use sources in this order:

1. CURRENT UNIT NOTES - primary source for what students are learning and what they already know.
2. CURRENT UNIT ASSESSMENT PLAN - primary source for section timing, I-can statements, learning targets, DOK expectations, and when concepts become eligible.
3. THIS PM - gold-standard format, workflow, equipment assumptions, legacy activity catalog, and design rules.
4. LEGACY ACTIVITY CATALOG IN THIS PM - inspiration / reusable activity ideas only.
5. General physics knowledge - only to fill practical instructional details that do not contradict or get ahead of the current notes/assessment plan.

Never silently introduce later-unit mathematics, terminology, formulas, or concepts because they appeared in an old activity.
If an old activity contains later-course content, strip that content out or redesign the activity.

Do not trust old module numbers or old section names as current mappings.
Map every legacy activity conceptually to the CURRENT notes and assessment plan first.
Example from archive review: old 7.5 material fit current 7.4 better than current 7.5.

DEMO DESIGN CONTRACT
====================
Purpose:
A demo is a 5-8 minute spark of curiosity before the notes.
It should make students notice something, predict, argue, observe, confront an intuition, or ask a useful question.
It does NOT need to teach the whole section.

Student-facing demo HTML:
- Designed for screen projection, not student download.
- Minimal text.
- Large type readable across the room.
- Usually 4-6 short slides/screens.
- One main idea per slide.
- Prediction / observation / model-selection prompts are excellent.
- Do not bury students in procedural directions.
- Do not include long background reading.
- A demo may be only teacher equipment plus projected prompts.
- Images/diagrams may be used when they make the phenomenon clearer.

Demo slide progression often follows a pattern such as:
1. Present the phenomenon or challenge.
2. Make a prediction.
3. Observe.
4. Compare competing explanations/models.
5. Carry a question into the notes.

This is a pattern, not a quota. Use the number of slides that best fits 5-8 minutes.

Demo navigation:
Approved Unit 1 uses Back / Next controls and keyboard navigation.
The basic pattern is:

  const slides=[...document.querySelectorAll('.demo-slide')]; let i=0;
  function show(n){ i=Math.max(0,Math.min(slides.length-1,n)); slides.forEach((s,j)=>s.classList.toggle('active',j===i)); document.getElementById('counter').textContent=`${i+1} / ${slides.length}`; }
  document.getElementById('prev').onclick=()=>show(i-1);
  document.getElementById('next').onclick=()=>show(i+1);
  document.addEventListener('keydown',e=>{
    if(['ArrowRight','PageDown',' '].includes(e.key)) show(i+1);
    if(['ArrowLeft','PageUp'].includes(e.key)) show(i-1);
  });

Use the same pattern unless there is a clear reason not to.

Demo content rules:
- Prefer a real physical phenomenon when practical.
- Quick discrepant events are valuable.
- Do not front-load the vocabulary students are about to learn in notes unless the prompt needs it.
- It is okay for the demo to leave the class with an unresolved question.
- The final slide should usually bridge naturally into the guided annotated notes.
- A demo should not become a worksheet.
- A demo should not require students to download a file.
- If student recording is useful, keep it informal unless the section specifically benefits from a tiny written prediction.

INVESTIGATION DESIGN CONTRACT
=============================
Purpose:
The investigation comes after the section notes and gives students evidence, data, modeling, or a phenomenon to use with the model they just learned.

Default length:
- 20-30 minutes.
- Full 40-minute scientific-method lab only when justified by the section.

Preferred modality hierarchy:
1. Hands-on real-world evidence when practical and instructionally strong.
2. Vernier Graphical Analysis when sensors, video analysis, graphs, or student-generated data improve the learning.
3. Online simulation when it provides control, visibility, scale, repeatability, or phenomena that classroom equipment cannot provide as well.
4. CER / modeling / station evidence tasks when that best fits the learning target.

Do not force every section into the same lab format.
Choose the investigation type that best serves the section.

Vernier equipment assumptions:
Assume the same equipment that appeared in the legacy course remains available.
Vernier Graphical Analysis is strongly preferred when it adds real instructional value.
Examples include:
- motion detector,
- force sensor / force probe when appropriate,
- video analysis,
- position / velocity / time data,
- student-generated graphs,
- quantitative comparisons.

Do not add Vernier merely to say it was used.
Use it when the graph/data helps students see or test the physics more clearly.

Simulation rules:
- Prefer official sources such as PhET when a simulation is the right tool.
- Verify the current official URL during the build if a live link is used.
- Use simulations because they improve the investigation, not because they are convenient.
- Do not make every Day 2 screen-based.

Student investigation HTML:
- Designed for download into Notability.
- Letter-page friendly.
- Clear section headings.
- Generous response/workspace areas.
- Workspace heights should be adjustable with --ws inline values.
- Use tables when students are genuinely collecting or comparing data.
- Use diagrams/figures when they improve comprehension.
- Use CER when claim/evidence/reasoning is a natural fit, not as a quota.
- Include enough procedure to run independently or semi-independently.
- Avoid dense walls of text.
- Avoid unnecessary calculations not supported by the current notes.

Student investigation structure often includes:
- kicker / title / subtitle,
- learning target,
- research question or challenge,
- prediction / initial model,
- equipment/setup,
- numbered procedure or evidence phases,
- data / graph / observation area,
- analysis / model revision,
- conclusion or CER when appropriate.

Again, this is a flexible pattern, not a forced template.

GRAPH TOOL - AUTHORITATIVE RULES
================================
The teacher will upload the CURRENT graph tool with each build.
That uploaded graph tool overrides any remembered older copy.

The graph tool is authoritative for all graph styling and behavior.
Do not modify, refactor, restyle, simplify, optimize, or rewrite its existing code.

When a graph is needed:
1. Check whether an existing graph type can produce the needed figure.
2. If yes, use the graph tool rather than manually drawing the graph or substituting inline SVG.
3. Copy the graph tool in full as generate_graphs.py.
4. Append graph-generation blocks only below the final append marker.
5. Never insert or modify lines above the append marker.
6. Do not override graph styling in generation blocks.
7. Run the graph script and place generated images in that section's figures/ folder.
8. Verify every graph reference in the HTML resolves to an existing figure.

If a graph-tool-generated figure is actually used in a section, include generate_graphs.py in that section folder for reproducibility unless the teacher explicitly directs otherwise.
Do not include generate_graphs.py when no graph-tool figure is used.

DIAGRAM / FIGURE RULES
======================
Figures are instructional tools, not quotas.
Use as many as genuinely help, including zero.

Good uses:
- apparatus setup,
- geometry that is hard to describe verbally,
- force/vector arrangements,
- sample graph axes or expected trend,
- optical ray setup,
- circuit arrangement,
- wave setup,
- experimental station arrangement.

Avoid decorative images that do not help students perform or understand the activity.
Use local files in figures/ rather than fragile external image hotlinks.

CURRENT-COURSE SEQUENCING RULE
==============================
Before writing each activity, explicitly determine from the notes + assessment plan:
- What students know BEFORE this section.
- What this section introduces.
- What students are expected to do by the end of the section.
- Which equations / representations are currently legitimate.
- Which concepts belong later and must not appear yet.

This sequencing rule is mandatory.

Examples from the approved Unit 1 build:
- Section 1.1 investigation removed acceleration and energy analysis from the old bouncy-ball lab because those concepts belong later.
- Section 1.2 used velocity-time data but did not introduce acceleration analysis.
- Section 1.2 teacher guide explicitly avoids momentum language because momentum is taught later.
- Section 1.3 used vector-resultant ideas without prematurely turning the section into a trigonometric components lesson.

CONTENT QUALITY CHECK
=====================
Before finalizing each section, ask:

DEMO
- Is this genuinely interesting enough to spark the section?
- Can it be run in 5-8 minutes?
- Is the projected text minimal?
- Does it create a useful question rather than prematurely lecture the answer?
- Does it transition naturally into the guided notes?

INVESTIGATION
- Does this use what students just learned?
- Is the evidence actually capable of supporting the intended conclusion?
- Is it hands-on when hands-on is better?
- Is Vernier Graphical Analysis being used when it genuinely improves the activity?
- If using a simulation, does it offer something physical equipment cannot do as well?
- Are students being asked to reason, model, graph, compare, or revise rather than merely follow steps?
- Does it avoid concepts not yet taught?
- Is there enough Notability workspace?

TEACHER GUIDE
- Could the teacher run the activity from this guide without reopening the design conversation?
- Are expected results, timing, setup, and troubleshooting clear?
- Does the guide identify misconceptions without over-explaining obvious classroom moves?

UNIT 1 PROTOTYPE LESSONS TO PRESERVE
====================================
The prototype process established several important design lessons:

1. A demo is allowed to be unresolved.
   The best demos create the need for the notes rather than replacing the notes.

2. Observation and inference should be separated when the section needs scientific thinking.
   Unit 1.1 "The Hidden Bounce" is the key example.

3. Old activities can be excellent raw material but should be stripped of content students have not learned yet.

4. Vernier Graphical Analysis is a preferred course tool.
   Use real measured evidence when it helps make the model visible.

5. Teacher guides are first-class course resources, not afterthoughts.
   They should be linked from index pages and follow the student experience.

6. Investigations are student documents.
   They are meant to be downloaded into Notability and written on.

7. Demo student pages are projection documents.
   Do not design them like handouts.

8. Every section package includes figures/, even if empty.

9. Shared CSS is course-level infrastructure.
   Do not keep regenerating or repackaging it.

10. If the CSS standard changes, create a new portable-memory version.
    Do not let future builds drift silently away from the approved design.

NORMAL FINAL RESPONSE AFTER A UNIT BUILD
========================================
Keep the final response concise.
Provide two download links, one for each ZIP, for example:

  [Download Unit 2 Demos ZIP](...)
  [Download Unit 2 Investigations ZIP](...)

Optionally give a one-line summary of the activity arc if useful.
Do NOT output CSS links during normal builds because the CSS is already installed and frozen.
Only mention CSS if a deliberate CSS change was made, and if that happens the PM must be versioned again.
